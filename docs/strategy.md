### 判定窓・経過日・次の判定日

```
d = 今日 − S（日数。日付はすべて JST）
d ≥ 14 かつ d が 14 の倍数 → 今日は判定日。判定窓 = (今日 − 14)..(今日 − 1)、次の判定日 = 今日 + 14
それ以外                  → 経過日 = Day (d mod 14 + 1) / 14、判定窓 = max(F, 今日 − 13)..今日、
                             次の判定日 = S + 14 × (floor(d / 14) + 1)
```

例: 09-15 は Day 2 / 14・判定窓 09-02..09-15・次の判定日 09-28。09-28 は判定日（判定窓 09-14..09-27）。

### 判定指標と集計コマンド

- **IG**: 判定窓の `instagram.views` の**中央値** + `instagram.saved` の**合計**（`instagram` か `instagram.views` が null の回は除外）
- **YT**: 判定窓の `stats.views` の**中央値**（`stats.updatedAt` が null の回は除外）
- n は IG / YT で別々に数える。**n < 7 なら判定保留**。IG と YT を足したり平均したりしない

```bash
# FROM / TO = 判定窓（上の計算式）
FROM=2026-09-02; TO=2026-09-15
jq -r --arg from "$FROM" --arg to "$TO" '
  def median: sort | if length==0 then null elif length%2==1 then .[(length/2|floor)] else ((.[length/2-1]+.[length/2])/2) end;
  [.videos[] | select(.date >= $from and .date <= $to)] as $v
  | ($v | map(select(.stats.updatedAt != null) | (.stats.views // 0))) as $yt
  | ($v | map(select(.instagram != null and .instagram.views != null) | .instagram)) as $ig
  | "window=\($from)..\($to) posts=\($v|length)",
    "YT views median=\($yt|median) (n=\($yt|length))",
    "IG views median=\($ig|map(.views)|median) saved_sum=\($ig|map(.saved // 0)|add // 0) (n=\($ig|length))"
' data/performance-history.json
```

### モードの決め方（毎朝、アカウントごと）

モードは IG = 常に `対象外`、YT = `通常` / `切替候補` / `配信死亡モード` のいずれか。

1. **前回モード**（YT）= `docs/pdca/` の最新レポートの「ジャンル試行の状態」のモード列。節が無ければ上の表の「導入時の判定」（配信死亡 → `配信死亡モード（2026-09-14〜）`）。試行 # が前回と違えば引き継がず `通常` から
2. **今日の判定値** = 判定窓の指標を閾値に当てはめた結果（n < 7 なら判定保留）
3. **決定**（上から順に）:
   - 判定保留 → 前回モードのまま
   - 前回が `配信死亡モード` → **判定日かつ判定値が配信死亡以外**のときだけ出る（続行 → `通常`、切替候補 → `切替候補`）。それ以外は `配信死亡モード` のまま
   - 判定値が配信死亡 → `配信死亡モード` に入る（判定日でなくても。宣言日 = 今日）
   - 今日が判定日 → 判定値どおり（続行 → `通常`、切替候補 → `切替候補`）
   - それ以外 → 前回モードのまま

### 配信死亡モード中の日次 PDCA

1. **YT の数字で method 切り口を最適化しない**: YT が配信死亡モードの間は、YT views で angle method の TOP/WORST 比較・Method 提案・80/20 選定をしない（0 と 1 を比べても何も分からない）
   - このリポは IG が `対象外`（生きている）ので、**method の比較と 80/20 は IG の指標（`instagram.views`、参考に `saved`）だけで行う**。YT views を混ぜない
   - もし IG の判定窓 n < 7 などで IG の指標も使えない日は、method を性能データで選ばず、コンテンツ柱比率と選定制約だけで選ぶ
2. **YT への提案は構造実験だけ**: タイトル個別化 / 型変更 / ジャンル変更（いずれも IG の投稿内容を変えない方法に限る）。各提案に「何を変えるか / 何で測るか / 14 日後の合格ライン」を書く
3. **投稿は止めない**。ネタ調査・原稿生成は通常どおり。型の切替は人間が決めて PR で入れる（ルーチンは提案まで）

## ペルソナ（優先順）

### Primary: 技術投資判断をする立場のエンジニア / CTO
- 0→1 フェーズのスタートアップ、個人開発者、ソロCTO
- 「今どんな OSS が伸びているか」で技術選定する
- 受託・コンサルの発注元になりうる

### Secondary: 事業責任者 / PdM
- 技術の理解は浅いが、「何が来ているか」のキャッチアップには使う
- 動画で知識を得る → 自社で困った時に思い出される
- コンサル発注の発案者になりやすい

### Tertiary: 学習中のエンジニア
- フォロワー数は稼いでくれるが、直接の顧客にはなりにくい
- 無視はしないが、彼ら向けにチャンネルを歪めない

| NG | 理由 |

## 探索方針（Discovery Strategy）

GitHub Trending 本体は毎日 refresh される「ニュース」のため、news-first 課題は既に解決済み。
このチャンネルの探索は「**5 リポをどの角度で紹介するか**」の discovery に重点を置く。

### 英語優先原則

Trending に上がる OSS の一次情報は全て英語。README、ブログ、リリースノートを英語で読む。
日本語情報は基本使わない（遅れるか、薄い）。**入力は英語、出力は日本語**。

### 角度選定 Methods（カテゴリタグ）

| タグ | 説明 |
|---|---|
| `tech-deep` | README・コードを読んで技術的な独自性を解説 |
| `business-angle` | 「実案件で月○円削れる」「受託で組むなら〜」ビジネス視点（柱② 向け） |
| `comparison` | 類似 OSS との比較（類似ツールでの差別化を提示） |
| `ecosystem` | 周辺ツール・エコシステム全体での位置づけ |
| `use-case` | 具体的な利用シーン（ソロ開発、スタートアップ、大企業等） |
| `self-experiment` | 実際に触って所感（柱③ 向け） |
| `trend-pattern` | 「なぜこの週に OSS が流行っているか」のマクロ視点 |

### 推奨ソース（シード）

- GitHub Trending（基本情報源、固定）
- リポジトリ README（英語）
- メンテナーの blog / X
- Hacker News の該当 OSS のスレッド（評価・議論の宝庫）
- Reddit r/programming、言語別 subreddit
- Release notes / CHANGELOG
- 類似 OSS の README（comparison 用）

### 80/20 Exploit/Explore

- 過去 14 日で視聴率上位 3 位の angle method は 80% 使う（exploit）
- 残り 20% は新しい angle method を試す（explore）

### Meta PDCA（探し方 = 角度の PDCA）

> 冒頭の「ジャンル実験」節が優先する。**YT が配信死亡モードの間は、以下の method 比較・80/20 を IG の指標（`instagram.views`）だけで行い、YT views を根拠にしない**。

毎日のルーチンで以下を分析:

1. 直近 14 日の `performance-history.json` から **method → 平均 views** テーブル
   - YouTube は `stats.views`、Instagram Reels は `instagram.views`（加えて `reach` / `shares` / `saved`）を**別列で並べる**。両者を合算しない（計測定義が違う）
   - `instagram` が `null` の動画は IG 投稿と突き合わせ不能だった回。IG 側の平均から除外する
   - IG insights は最大 48 時間遅れる。前日・当日分の IG 値は暫定として扱う
2. TOP 3 / WORST 3 method を特定
3. 「今日の 5 リポをどの method で料理するか」を 80/20 ルールで決める
4. 新しい angle のアイデアは PDCA レポートの「Method 提案」セクションに記録

### performance-history.json の指標

| キー | 取得元 | 更新 |
|---|---|---|
| `stats.views` / `likes` / `comments` | YouTube Data API v3 | `fetch-stats.mjs`（直近 14 日） |
| `instagram.mediaId` | 投稿時に `upload-instagram.mjs` → `record-upload.mjs` が記録。無い回は `fetch-stats.mjs` が IG 投稿一覧と JST 投稿日で突き合わせて復元 | 投稿時 / 初回取得時 |
| `instagram.views` / `reach` / `likes` / `comments` / `shares` / `saved` | Instagram Graph API `/{ig-media-id}/insights`（`plays` は廃止済みのため `views` を使用） | `fetch-stats.mjs`（直近 14 日 + 未取得の回） |

手動で更新だけしたいときは `gh workflow run fetch-stats.yml`（動画生成・投稿はしない）。
