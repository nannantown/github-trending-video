### 判定窓・経過日・次の判定日と集計コマンド

d = 今日 − S（日数。日付はすべて JST）

| 条件 | 経過日 | 判定窓 | 次の判定日 |
|---|---|---|---|
| d < 0 | 未開始（S が未来の日付 = 台帳の書き間違い。前回モードと method 方針をそのまま続け、レポートの「注意」行に書く） | — | — |
| d ≥ 14 かつ d が 14 の倍数 | **判定日** | (今日 − 14)..(今日 − 1) | 今日 + 14 |
| それ以外 | Day (d mod 14 + 1) / 14 | max(F, 今日 − 13)..今日 | S + 14 × (floor(d / 14) + 1) |

例（IG の行、S = 2026-09-14）: 09-15 は Day 2 / 14・判定窓 09-02..09-15・次の判定日 09-28。09-28 は判定日（判定窓 09-14..09-27）。09-29 は Day 2 / 14（次の判定日 10-12）。
例（YT の行、S = F = 2026-09-16）: 09-16 は Day 1 / 14・判定窓 09-16..09-16・次の判定日 09-30。09-17 は Day 2 / 14・判定窓 09-16..09-17。09-30 は判定日（判定窓 09-16..09-29、次の判定日 10-14）。

下のコマンドは、S と F を台帳の値にすれば、今日の日付から判定窓・経過日・次の判定日・判定指標をまとめて出す（日付を手で書き換えない）。IG と YT で S / F が違うときは行ごとに実行し、該当する側の数字を使う。

```bash
TODAY=$(TZ=Asia/Tokyo date +%Y-%m-%d); S=2026-09-14; F=2026-04-06   # IG の行。YT の行は S=2026-09-16; F=2026-09-16 で実行する
jq -r --arg today "$TODAY" --arg s "$S" --arg f "$F" '
  def day: strptime("%Y-%m-%d") | mktime / 86400 | floor;
  def ymd: . * 86400 | strftime("%Y-%m-%d");
  def median: sort | if length==0 then null elif length%2==1 then .[(length/2|floor)] else ((.[length/2-1]+.[length/2])/2) end;
  ($today|day) as $t | ($s|day) as $sd | ($f|day) as $fd | ($t - $sd) as $d
  | if $d < 0 then "today=\($today) status=未開始"
    else
      (if ($d >= 14 and ($d % 14) == 0) then {status:"判定日", from:($t-14|ymd), to:($t-1|ymd), next:($t+14|ymd)}
       else {status:"Day \(($d % 14)+1) / 14", from:([$fd, $t-13]|max|ymd), to:$today, next:($sd + 14*((($d/14)|floor)+1)|ymd)} end) as $w
      | [.videos[] | select(.date >= $w.from and .date <= $w.to)] as $v
      | ($v | map(select(.stats.updatedAt != null) | (.stats.views // 0))) as $yt
      | ($v | map(select(.instagram != null and .instagram.views != null) | .instagram)) as $ig
      | "today=\($today) status=\($w.status) window=\($w.from)..\($w.to) next_judgment=\($w.next) posts=\($v|length)",
        "YT views median=\($yt|median) (n=\($yt|length))",
        "IG views median=\($ig|map(.views)|median) saved_sum=\($ig|map(.saved // 0)|add // 0) (n=\($ig|length))"
    end
' data/performance-history.json
```

- 過去の判定日 J の判定（遅延判定）を出すときは、`TODAY` に J を入れて実行する（status=判定日、判定窓 (J − 14)..(J − 1) になる）
- jq の日付関数が使えない環境では、上の表どおりに `date -d` で判定窓を出し、同じ条件（YT は `stats.updatedAt` あり、IG は `instagram.views` あり）で中央値と合計を出す

### 判定指標

- **IG**: 判定窓の `instagram.views` の**中央値**と、`instagram.saved` の**合計**（別々の 2 指標で、足さない）。`instagram` か `instagram.views` が null の回は除外
- **YT**: 判定窓の `stats.views` の**中央値**。`stats.updatedAt` が null の回は除外
- n は IG / YT で別々に数える。**n < 7 なら判定保留**。IG と YT の数字を足したり平均したりしない
- 朝ルーチンの時点では当日分は未投稿で、前日分も統計・insights が未取得のことが多い（除外されるので、通常日の n は最大 12 前後）

### 閾値（表の上から順に当てはめ、最初に該当した行が判定値。初期値・仮置き）

| 判定 | IG（参考。対象外なので判定に使わない） | YT |
|---|---|---|
| **配信死亡** | views 中央値 < 10 **かつ** 保存合計 < 5 | views 中央値 < 5 |
| **切替候補** | views 中央値 < 50 **かつ** 保存合計 < 5 | views 中央値 < 20 |
| **続行** | 上記以外 | 上記以外 |

- 判定は指標だけで機械的に出す（「もう少し様子を見たい」は理由にしない）。閾値はルーチンが変えない（おかしいと思ったら「戦略更新提案」に書く）
- 同じ試行で判定日の「続行」が 3 回（42 日）続いたら、その判定日に「伸びしろが残っているか」を一言添える
- IG が切替候補・配信死亡の域に落ちても切替提案はしない。「戦略更新提案」に数字だけを書き、オーナーの判断を仰ぐ

### モードの決め方（毎朝、アカウントごと）

モードは IG = 常に `対象外`、YT = `通常` / `切替候補` / `配信死亡モード` のいずれか。**YT のモードが変わるのは判定日（と遅延判定）だけ**で、それ以外の日は前回モードを続ける（行ったり来たりを防ぐ）。

1. **前回モード** = `docs/pdca/` の `YYYY-MM-DD.md` のうち、**今日より前の日付で「ジャンル試行の状態」表のモード列が読める最新のもの**のモード列。表の無いレポート（「未導入」の 2 行だけ・ルーチンの失敗など）は飛ばして、さらに前の日付を見る。1 本も無いときだけ、上の台帳の「導入時の判定」（配信死亡 → `配信死亡モード（2026-09-14〜）`）。**新しい試行が始まっても前回モードを引き継ぐ**（新しい試行の最初の判定日に、その試行の数字で判定し直す）
2. **遅延判定**: 今日より前の直近の判定日 J について、J 以降の日付のレポートに「ジャンル判定」節が無ければ（ルーチンの失敗・導入の遅れなど）、今日まず J の判定を窓 (J − 14)..(J − 1) で出し、3. の判定日と同じ扱いでモードを決め直してから今日の分に進む。判定日は S + 14k（k ≥ 1）だけで、S 当日（2026-09-14 の「導入時の判定」）は判定日ではないので、遅延判定の対象にしない
3. **決定**:
   - **今日が判定日（または遅延判定）** → 判定値どおり: 配信死亡 → `配信死亡モード`（前回から続くなら宣言日はそのまま、新しく入るなら宣言日 = その判定日）/ 切替候補 → `切替候補` / 続行 → `通常` / 判定保留（n < 7）→ 前回モードのまま
   - **それ以外の日** → 前回モードのまま。今日の判定値が配信死亡なのにモードが `配信死亡モード` でないときは、レポートに「注意」行を書く（モードの変更は次の判定日）

### 通常・切替候補のときの日次 PDCA（Meta PDCA の補足）

- angle method の比較・80/20 は、**型の初回投稿日 F 以降の回だけ**で行う（新しい型の序盤に古い型の数字を混ぜない）。method 分析に使う「直近 14 日」は判定窓とは別で、**今日より前の 14 日**（今日 − 14..今日 − 1）
- method の順位は**アカウントごとに**付ける（IG の TOP 3 と YT の TOP 3 を別々に出し、合算スコアを作らない）。**YT が配信死亡モードの間は IG の TOP 3 だけを使う**
- YT が切替候補のときは、判定日に次の試行候補を 2〜3 案出す（IG の投稿内容を変えない方法に限る）

### YT が配信死亡モードの間の日次 PDCA

1. **YT の数字で angle method を最適化しない**: YT views で method の TOP/WORST 比較・Method 提案・80/20 選定をしない。**method の比較と 80/20 は IG の指標（`instagram.views`、参考に `saved`）だけで行う**
   - IG の指標も使えない日（判定窓の IG n < 7 など）は、method を性能データで選ばず、「直近 2 日と同じ method を連続で選ばない」「週に最低 1 日は柱②か③」を満たす method のうち**直近 14 日の使用回数（`data/performance-history.json` の、今日より前の直近 14 日の `discovery.method` で数える）が少ないもの**を選ぶ（同数なら下の「角度選定 Methods」表の上から）
2. **YT への提案は構造実験だけ**: タイトル個別化 / 型変更 / ジャンル変更（いずれも IG の投稿内容を変えない方法に限る）。各提案に「何を変えるか / 何で測るか / 14 日後の合格ライン」を書く。合格ラインの既定は上の閾値表の「続行」域（YT views 中央値 ≥ 20）で、配信死亡を抜けるだけの線（≥ 5）を合格にしない
3. **提案はレポートに書くだけ**: 当日の原稿・タイトル・`data/enriched-trending.json` には反映しない（5 プロジェクト構成・スキーマ・必須フィールドは従来どおり。反映すると動画生成が失敗しうる）。次の試行候補や構造実験は手持ちのデータと知識で短く書き、Web 調査に時間を使わない
4. **新しい試行が走っている間**（YT の試行 # が #1 以降で、まだ最初の判定日前）は、「構造実験の提案」節に `実行中: 試行 #n（<内容>）Day N / 14` と書き、追加の提案は判定日まで控える（変数を増やさない）。台帳の注記で別カードが準備中の試行があり、まだ初回投稿が無い間も同じで、`準備中: <内容>（別カードで実装中）` とだけ書き、同じ案を毎朝書き直したり別案を足したりしない
5. **投稿は止めない**。ネタ調査・原稿生成は通常どおり。型の切替は人間が決めて PR で入れる

## ペルソナ（優先順）

### Primary: 技術投資判断をする立場のエンジニア / CTO
- 0→1 フェーズのスタートアップ、個人開発者、ソロCTO
- 「今どんな OSS が伸びているか」で技術選定する
- 受託・コンサルの発注元になりうる

### Secondary: 事業責任者 / PdM
- 技術の理解は浅いが、「何が来ているか」のキャッチアップには使う
- 動画で知識を得る → 自社で困った時に思い出される
- コンサル発注の発案者になりやすい

### Tertiary: 学習中のエンジニア
- フォロワー数は稼いでくれるが、直接の顧客にはなりにくい
- 無視はしないが、彼ら向けにチャンネルを歪めない

## 探索方針（Discovery Strategy）

GitHub Trending 本体は毎日 refresh される「ニュース」のため、news-first 課題は既に解決済み。
このチャンネルの探索は「**5 リポをどの角度で紹介するか**」の discovery に重点を置く。

### 英語優先原則

Trending に上がる OSS の一次情報は全て英語。README、ブログ、リリースノートを英語で読む。
日本語情報は基本使わない（遅れるか、薄い）。**入力は英語、出力は日本語**。

### 角度選定 Methods（カテゴリタグ）

| タグ | 説明 |
|---|---|
| `tech-deep` | README・コードを読んで技術的な独自性を解説 |
| `business-angle` | 「実案件で月○円削れる」「受託で組むなら〜」ビジネス視点（柱② 向け） |
| `comparison` | 類似 OSS との比較（類似ツールでの差別化を提示） |
| `ecosystem` | 周辺ツール・エコシステム全体での位置づけ |
| `use-case` | 具体的な利用シーン（ソロ開発、スタートアップ、大企業等） |
| `self-experiment` | 実際に触って所感（柱③ 向け） |
| `trend-pattern` | 「なぜこの週に OSS が流行っているか」のマクロ視点 |

### 推奨ソース（シード）

- GitHub Trending（基本情報源、固定）
- リポジトリ README（英語）
- メンテナーの blog / X
- Hacker News の該当 OSS のスレッド（評価・議論の宝庫）
- Reddit r/programming、言語別 subreddit
- Release notes / CHANGELOG
- 類似 OSS の README（comparison 用）

### 80/20 Exploit/Explore

- 過去 14 日で視聴率上位 3 位の angle method は 80% 使う（exploit）
- 残り 20% は新しい angle method を試す（explore）

### Meta PDCA（探し方 = 角度の PDCA）

> 冒頭の「ジャンル実験」節が優先する。以下の method 比較・80/20 は**型の初回投稿日 F 以降の回だけ**で、**アカウントごとに**（IG と YT を合算せず）行う。**YT が配信死亡モードの間は IG の指標（`instagram.views`）だけを使い、YT views を根拠にしない**。

毎日のルーチンで以下を分析:

1. 直近 14 日の `performance-history.json` から **method → 平均 views** テーブル
   - YouTube は `stats.views`、Instagram Reels は `instagram.views`（加えて `reach` / `shares` / `saved`）を**別列で並べる**。両者を合算しない（計測定義が違う）
   - `instagram` が `null` の動画は IG 投稿と突き合わせ不能だった回。IG 側の平均から除外する
   - IG insights は最大 48 時間遅れる。前日・当日分の IG 値は暫定として扱う
2. TOP 3 / WORST 3 method を特定
3. 「今日の 5 リポをどの method で料理するか」を 80/20 ルールで決める
4. 新しい angle のアイデアは PDCA レポートの「Method 提案」セクションに記録

### performance-history.json の指標

| キー | 取得元 | 更新 |
|---|---|---|
| `stats.views` / `likes` / `comments` | YouTube Data API v3 | `fetch-stats.mjs`（直近 14 日） |
| `instagram.mediaId` | 投稿時に `upload-instagram.mjs` → `record-upload.mjs` が記録。無い回は `fetch-stats.mjs` が IG 投稿一覧と JST 投稿日で突き合わせて復元 | 投稿時 / 初回取得時 |
| `instagram.views` / `reach` / `likes` / `comments` / `shares` / `saved` | Instagram Graph API `/{ig-media-id}/insights`（`plays` は廃止済みのため `views` を使用） | `fetch-stats.mjs`（直近 14 日 + 未取得の回） |

手動で更新だけしたいときは `gh workflow run fetch-stats.yml`（動画生成・投稿はしない）。
